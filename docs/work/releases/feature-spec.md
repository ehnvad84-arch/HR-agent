# Спецификация: releases

Статус: черновик
PRD: —

## Зачем — главная сессия

Портал работает у заказчика на 10.20.10.115: там накоплена база резюме, ключи hh, выгрузки 1С, учётные записи.
Новые фичи (воронка, реестр кандидатов, бот hh и др.) должны накатываться инженерами заказчика поверх
работающей версии по одной команде и не ломать данные, интеграции и прежнюю версию. У каждой версии есть номер,
список изменений и путь назад.

## Поведение (BDD) — главная сессия

Действующие лица: **инженер** (обновляет рабочий сервер), **разработчик** (агент на пробном VPS, готовит версии).

### S1: Версия видна

- **Дано** на сервере установлена версия v1.1.0
- **Когда** инженер выполняет `python -m hr.cli version` или пользователь открывает «Схему»
- **Тогда** видно `v1.1.0`, сколько миграций применено и нет ли неприменённых; `/api/version` отдаёт то же без входа
  (только номер версии, без настроек)

### S2: Обновление на одну или несколько версий вперёд

- **Дано** на сервере v1.0.0, в GitHub есть v1.1.0 и v1.2.0
- **Когда** инженер выполняет `scripts/update.sh v1.2.0`
- **Тогда** скрипт по шагам: проверки → остановка таймеров и портала → копия базы (если есть новые миграции) →
  код версии → зависимости → миграции v1.1.0 и v1.2.0 по порядку → запуск → проверка, что портал отвечает и
  показывает v1.2.0; в конце — итог одним экраном и запись в журнал версий
- **И** резюме, история, `.env`, `server/data`, токены hh, учётные записи и настройки, поменянные в портале,
  остались прежними

### S3: Проверки до остановки портала

- **Дано** одно из: в коде на сервере есть ручные правки; версия не найдена; версия старше текущей; на диске меньше
  места, чем нужно копии базы; идёт фоновая задача (сбор hh) дольше заданного ожидания
- **Когда** инженер запускает `update.sh`
- **Тогда** портал не останавливается, скрипт называет причину и что сделать; ручные правки перечислены по файлам

### S4: Новая версия не поднялась — автоматический возврат кода

- **Дано** миграции прошли, но портал после запуска не отвечает или показывает не ту версию
- **Когда** `update.sh` доходит до проверки
- **Тогда** скрипт возвращает код и зависимости прежней версии, запускает портал, таймеры и сообщает: «обновление не
  прошло, работает vX.Y.Z, база обновлена и совместима, копия — <файл>»

### S5: Откат по решению людей

- **Дано** v1.2.0 работает, но отделу персонала что-то мешает
- **Когда** инженер выполняет `scripts/rollback.sh v1.1.0`
- **Тогда** возвращается код v1.1.0 без изменения базы; всё, что сделали рекрутеры после обновления, сохраняется;
  v1.1.0 работает на базе v1.2.0

### S6: Прежняя версия работает на новой базе (правило совместимости)

- **Дано** миграция новой версии
- **Когда** разработчик готовит версию
- **Тогда** миграция только добавляет: новые таблицы, поля с значением по умолчанию или NULL, индексы, настройки
  `ON CONFLICT DO NOTHING`; удаление, переименование, смена типа и ужесточение ограничений — только в следующей
  версии после того, как код перестал на них опираться, и только с пометкой в миграции и в списке изменений
- **И** тест не пропускает такую миграцию без пометки; проверка совместимости запускает код прошлой версии на базе
  новой и проходит его проверки

### S7: Выпущенная миграция неизменна

- **Дано** миграция вошла в выпущенную версию
- **Когда** её файл меняют или удаляют
- **Тогда** тест падает; исправление — только новой миграцией; два файла с одним номером тоже роняют тест

### S8: Настройки, поменянные людьми, не перетираются

- **Дано** руководитель отдела персонала поменял порог в портале
- **Когда** новая версия меняет значение этой настройки по умолчанию
- **Тогда** у кого настройка не трогалась — новое значение и запись в `agent_change`; у кого поменяна — остаётся её
  значение, в итоге обновления — строка «настройка X оставлена как есть»

### S9: Новые ключи и интеграции выключены, пока не заданы

- **Дано** новая версия добавляет переменную `.env` (например, токен бота)
- **Когда** инженер обновляется, не вписав её
- **Тогда** портал работает, новая интеграция выключена; итог обновления и `check_env.py` называют, каких
  переменных нет (имена, без значений), список изменений говорит, где их взять

### S10: Список изменений для каждой версии

- **Дано** готовится версия
- **Когда** разработчик её выпускает
- **Тогда** в `CHANGELOG.md` есть раздел версии: что нового для людей, новые миграции, новые переменные `.env`,
  ручные шаги, можно ли откатиться; без раздела выпуск не собирается

### S11: Первый переход с установки из архива

- **Дано** на рабочем сервере v1.0.0 из ZIP, без git
- **Когда** инженер проходит раздел «Первый раз» инструкции обновления
- **Тогда** установка становится копией репозитория на версии v1.0.0 с ключом GitHub только на чтение; `.env`,
  `server/data`, база и службы не меняются; `hr.cli version` показывает v1.0.0 и 0 неприменённых миграций

## Вне рамок — главная сессия

- Обновление без остановки (две копии портала): портал внутренний, простой — несколько минут вечером или до 8:00.
- Откат базы как штатный путь: копия базы только на крайний случай, восстановление — вручную по инструкции.
- Сборка образов Docker, CI-деплой: обновляют инженеры командой на сервере.
- Резервное копирование рабочей базы по расписанию — решает ИТ заказчика.
- Доступ агента к рабочему серверу: его нет и не будет.

## Решения — главная сессия

| Вопрос | Выбрано | Почему | Отвергнуто |
|---|---|---|---|
| Доставка версии | git-тег из GitHub, на сервере ключ только на чтение | одна команда, видно, что поменяно руками | ZIP каждой версии — ручной труд, нет проверки правок |
| Откат | только код; база совместима с прошлой версией | действия рекрутеров после обновления не теряются | восстановление базы из копии как штатный путь |
| Простой | портал и таймеры остановлены на время обновления | просто и надёжно для внутреннего портала | две копии и переключение |
| Номера | SemVer `vX.Y.Z`: Z — исправления, Y — фичи, X — несовместимое | видно масштаб | по дате |
| v1.0.0 | тег на `2bf9c68` — то, что ушло заказчику в архиве | первая точка отсчёта | — |
| Пробный VPS | проверки обновления — на маленьких базах `*_test`, после удаляются | решение человека 10.11: резюме сюда не грузим, диск бережём | репетиция на копии рабочей базы |

## Открытые вопросы

- Сколько копий базы перед обновлением хранить на рабочем сервере (по умолчанию 2, база около 10 ГБ).
- Кто ставит тег версии в GitHub: агент после мержа по слову человека или сам человек.
- Ключ GitHub только на чтение: публичный ключ инженеры присылают владельцу репозитория, тот добавляет его в Deploy
  keys — нужен человек.
