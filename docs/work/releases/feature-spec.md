# Спецификация: releases

Статус: черновик
PRD: —

## Зачем — главная сессия

Портал работает у заказчика на 10.20.10.115: там накоплена база резюме, ключи hh, выгрузки 1С, учётные записи.
Новые фичи (воронка, реестр кандидатов, бот hh и др.) должны накатываться инженерами заказчика поверх
работающей версии по одной команде и не ломать данные, интеграции и прежнюю версию. У каждой версии есть номер,
список изменений и путь назад.

## Поведение (BDD) — главная сессия

Действующие лица: **инженер** (обновляет рабочий сервер), **разработчик** (агент на пробном VPS, готовит версии).

### S1: Версия видна

- **Дано** на сервере установлена версия v1.1.0
- **Когда** инженер выполняет `python -m hr.cli version` или пользователь открывает «Схему»
- **Тогда** `hr.cli version` показывает `v1.1.0`, сколько миграций применено и нет ли неприменённых; в «Схеме» и в
  `/api/version` без входа — только номер и дата версии

### S2: Обновление на одну или несколько версий вперёд

- **Дано** на сервере v1.0.0, в GitHub есть v1.1.0 и v1.2.0
- **Когда** инженер выполняет `scripts/update.sh v1.2.0` (самый первый раз с v1.0.0, где скрипта нет, — командой из
  инструкции: скрипт берётся из тега)
- **Тогда** скрипт по шагам: проверки → остановка таймеров и портала → копия базы (если есть новые миграции) →
  код версии → зависимости → миграции v1.1.0 и v1.2.0 по порядку → запуск → проверка, что портал отвечает и
  показывает v1.2.0; в конце — итог одним экраном и запись в журнал версий
- **И** резюме, история, `.env`, `server/data`, токены hh, учётные записи и настройки, поменянные в портале,
  остались прежними

### S3: Проверки до остановки портала

- **Дано** одно из: в коде на сервере есть ручные правки; версия не найдена; версия старше текущей; на диске меньше
  места, чем нужно копии базы; идёт фоновая задача (сбор hh) дольше заданного ожидания
- **Когда** инженер запускает `update.sh`
- **Тогда** портал не останавливается, скрипт называет причину и что сделать; ручные правки перечислены по файлам

### S4: Новая версия не поднялась — автоматический возврат кода

- **Дано** миграции прошли, но портал после запуска не отвечает или показывает не ту версию
- **Когда** `update.sh` доходит до проверки
- **Тогда** скрипт возвращает код и зависимости прежней версии, запускает портал, таймеры и сообщает: «обновление не
  прошло, работает vX.Y.Z, база обновлена и совместима, копия — <файл>»

### S5: Откат по решению людей

- **Дано** v1.2.0 работает, но отделу персонала что-то мешает
- **Когда** инженер выполняет `scripts/rollback.sh v1.1.0`
- **Тогда** возвращается код v1.1.0 без изменения базы; всё, что сделали рекрутеры после обновления, сохраняется;
  v1.1.0 работает на базе v1.2.0; откат ниже v1.1.0 (версии без механизма версий) скрипт не делает

### S6: Прежняя версия работает на новой базе (правило совместимости)

- **Дано** миграция новой версии
- **Когда** разработчик готовит версию
- **Тогда** миграция только добавляет: новые таблицы, поля с значением по умолчанию или NULL, индексы, настройки
  `ON CONFLICT DO NOTHING`; удаление, переименование, смена типа и ужесточение ограничений — только в следующей
  версии после того, как код перестал на них опираться, и только с пометкой в миграции и в списке изменений
- **И** тест не пропускает такую миграцию без пометки; проверка совместимости запускает код прошлой версии на базе
  новой и проходит его проверки

### S7: Выпущенная миграция неизменна

- **Дано** миграция вошла в выпущенную версию
- **Когда** её файл меняют или удаляют
- **Тогда** тест падает; исправление — только новой миграцией; два файла с одним номером тоже роняют тест

### S8: Настройки, поменянные людьми, не перетираются

- **Дано** руководитель отдела персонала поменял порог в портале
- **Когда** новая версия меняет значение этой настройки по умолчанию
- **Тогда** у кого настройка не трогалась — новое значение и запись в `agent_change`; у кого поменяна — остаётся её
  значение, в итоге обновления — строка «настройка X оставлена как есть»

### S9: Новые ключи и интеграции выключены, пока не заданы

- **Дано** новая версия добавляет переменную `.env` (например, токен бота)
- **Когда** инженер обновляется, не вписав её
- **Тогда** портал работает, новая интеграция выключена; итог обновления и `hr.cli env-missing` называют, каких
  переменных нет (имена, без значений), список изменений говорит, где их взять

### S10: Список изменений для каждой версии

- **Дано** готовится версия
- **Когда** разработчик её выпускает
- **Тогда** в `CHANGELOG.md` есть раздел версии: что нового для людей, новые миграции, новые переменные `.env`,
  ручные шаги, можно ли откатиться; без раздела выпуск не собирается

### S11: Первый переход с установки из архива

- **Дано** на рабочем сервере v1.0.0 из ZIP, без git
- **Когда** инженер проходит раздел «Первый раз» инструкции обновления
- **Тогда** установка становится копией репозитория на версии v1.0.0 с ключом GitHub только на чтение; `.env`,
  `server/data`, база и службы не меняются, прежний `.venv` становится `.venvs/v1.0.0` со ссылкой `.venv` на него; `git describe --tags` = v1.0.0, `git status` чистый (у v1.0.0 нет
  `hr.cli version`; запись `baseline` в журнал версий делает первый `update.sh`)

### S12: Одна свежая копия базы

- **Дано** на сервере лежит копия базы недельной давности
- **Когда** срабатывает недельный таймер (ставят инженеры по образцу из инструкции) или `update.sh` перед миграциями
- **Тогда** пишется новая копия; только после успешной записи и проверки она заменяет прежнюю; копия всегда одна
- **И** если запись не удалась (мало места, ошибка), прежняя копия остаётся, а обновление не начинается

## Вне рамок — главная сессия

- Обновление без остановки (две копии портала): портал внутренний, простой — несколько минут вечером или до 8:00.
- Откат базы как штатный путь: копия базы только на крайний случай, восстановление — вручную по инструкции.
- Сборка образов Docker, CI-деплой: обновляют инженеры командой на сервере.
- Полноценное резервное копирование (история копий, вынос на другой сервер) — решает ИТ заказчика; здесь только одна
  свежая копия (S12).
- Доступ агента к рабочему серверу: его нет и не будет.

## Архитектура, API и данные — backend-architect

  «Миграции», «Переменные .env», «Ручные шаги», «Откат» (да/нет и почему). Тег — на коммит `main`, где VERSION = тег.

  `status(conn) -> {code, db, applied, pending[], ahead[]}` (`code` на установке без VERSION — `git describe --tags

  `ahead` — применённые миграции, которых нет в коде (норма после отката, S5). В `db.py:79–97` выделить
  `pending(conn)`, поведение `migrate()` не меняется.
- `hr/cli.py:15` — новые команды: `version` (S1; выход 3 — есть неприменённые), `migrate --pending`,
  `jobs-running` (S3: `ops.job_run` с `finished_at IS NULL` моложе настройки `load_stuck_hours`; выход 4 — идут;

  `.env.example`, которых нет или пусто в `.env`; значения не печатает), `job-record` (итог копии базы в `ops.job_run`,
  job `db_copy`; неудачу видно в истории задач и по коду выхода таймера).
- `hr/api/version.py`: `GET /api/version` без входа (роутер регистрируется в `hr/main.py:36–43`) → `200 {"version": "v1.1.0",
  "date": "2026-11-10"}`, больше ничего;
  `guide.js` берёт строку оттуда (S1). Не `base.read`, тест `routes_unscoped` его не касается.
- Тесты `tests/test_release.py`: S7 — `migrations/RELEASED.sha256` (`sha256  имя` всех выпущенных миграций): файл есть,
  сумма совпадает, номера `NNN_` уникальны; S6 — линтер DDL по файлам вне замка; S10 — VERSION = первый раздел
  CHANGELOG, все 5 подразделов, новые миграции перечислены; S1 — у `/api/version` ровно два ключа; S8 — оба пути
  `ops.change_default`, включая «ключа нет в settings».
- Скрипты (bash, `set -euo pipefail`, `flock` на `BACKUP_DIR/.lock` берётся после повторного `exec`; `db_copy.sh` при
  `RUWARE_LOCK_HELD=1` от родителя его не берёт, тег проверяется `^v[0-9]+\.[0-9]+\.[0-9]+$`
  до любого использования, иначе выход 2):
  - `scripts/release.sh vX.Y.Z [--dry-run]` (разработчик): `ruff`, `qa-test pytest`, `pip-audit`, `compat_check.sh`, VERSION, дописать
    замок, коммит; тег на `main` после мержа и `git push origin vX.Y.Z` — агент.
  - `scripts/db_copy.sh [--check-space]` (S12): недельный таймер у заказчика (образец юнита — в `update.conf.example`
    и инструкции; `install_autostart.sh` пробного VPS не трогаем — здесь копии не делаем) и шаг `update.sh`. Пишет `ruware.dump.new` (`PG_DUMP -Fc`, `umask 077`) → `pg_restore --list` и размер > 0 →
    `mv -f` поверх `ruware.dump` (атомарно в одном каталоге) + `ruware.dump.info` (версия, время). Провал → `.new`
    удаляется, прежняя копия цела, выход ≠ 0. Место: свободно в `BACKUP_DIR` ≥ `pg_database_size × SPACE_FACTOR`
    (прежняя копия лежит до замены, считаем под одну новую).
  - `scripts/update.sh`, `scripts/rollback.sh` — на сервере. Конфиг `server/update.conf` (в `.gitignore`, образец
    `update.conf.example`): `STOP_CMD`, `START_CMD` (службы и таймеры: у заказчика свой планировщик), `CHECK_URL`
    (`http://127.0.0.1:8000/api/version`), `START_WAIT_S=60`, `BACKUP_DIR` (вне репозитория), `SPACE_FACTOR=1.2`,
    `PG_DUMP` (pg_dump 16 или `docker exec …`), `JOB_WAIT_MIN=30`.
  - `scripts/compat_check.sh <прошлый тег>` — S6, ниже.

**update.sh vX.Y.Z** (провал на шагах 1–4 — портал не останавливался, S3):
Запускается из корня репозитория (`git rev-parse --show-toplevel`). Код и venv цели готовятся рядом:
`git worktree add --detach .releases/<тег> <тег>` — все вызовы `hr.cli` до переключения идут кодом цели, у v1.0.0 их нет.
1. `git fetch --tags origin` без `--force`; при `RUWARE_UPDATE_REEXEC` пусто — `exec` версии скрипта из тега
   (`git show <тег>:server/scripts/update.sh` во временный файл, `RUWARE_UPDATE_REEXEC=1`); затем `flock`.
2. Дерево: `git status --porcelain` (отслеживаемые и новые неигнорируемые) пусто, иначе список; `server/.venv` — симлинк,
   иначе стоп со ссылкой на S11; тег есть; текущая — `git describe --tags --exact-match HEAD`; `sort -V`: тег новее
   (равен — «уже установлена», 0); если в теге новые миграции — `db_copy.sh --check-space`.
3. Зависимости до остановки: `server/.venvs/<тег>` из `requirements.txt` цели; сеть упала — портал работает.
4. `hr.cli jobs-running` (код цели) раз в минуту до `JOB_WAIT_MIN`.
5. `STOP_CMD` (таймеры, затем портал), повтор `jobs-running`. Если `git diff --name-only HEAD <тег> -- server/migrations`
   не пуст — `RUWARE_LOCK_HELD=1 db_copy.sh`; провал → `START_CMD`, выход (S12).
6. `git checkout --detach <тег>`; `ln -sfn .venvs/<тег> server/.venv`; `hr.cli migrate` — печатает
   `ops.release_notice` своего прогона (S8). Упавшая миграция откатывается своей транзакцией (`db.py:93`), прошедшие
   остаются — они добавляющие.
7. `START_CMD`; опрос `CHECK_URL` до `START_WAIT_S`, `version` = тег.
8. Провал 6–7 (trap ERR/INT, S4): checkout прежнего тега, симлинк на прежний venv (без сети), `START_CMD`, проверка
   (прежняя ≥ v1.1.0 — `/api/version`, v1.0.0 — `/` отвечает 200), `release-record --kind auto_rollback` кодом цели из
   `.releases/<тег>`, сообщение S4 с именем копии.
9. Итог одним экраном: было → стало, миграции, notices, `env-missing`, «Ручные шаги» из CHANGELOG тега, копия;
   `release-record --kind update` (первый раз ещё и `baseline` прежней версии). `.releases/<тег>` удаляется; в `.venvs/`
   остаются текущая и прошлая.

**rollback.sh vX.Y.Z** (S5): шаги 1 (без exec), 2 (цель старше текущей), 4; цель ≥ v1.1.0, не старше `from_version`
последнего удачного обновления, и ни у одной пропускаемой версии в CHANGELOG нет «Откат: нет» — иначе отказ с причиной.
`release-record` пишется кодом текущей версии до checkout. STOP → checkout → venv цели (есть — симлинк, нет —
установка) → **без `migrate`** → START → проверка `/api/version`.

Зависимости: свой venv на версию в `server/.venvs/<тег>`, `server/.venv` — симлинк, юниты не меняются
(`install_autostart.sh:40`); откат без сети за секунды; хранятся текущая и прошлая (~150 МБ каждая); в `.gitignore`
добавить `.venv` без слэша (сейчас `.venv/` ловит только каталог).

**Совместимость N-1 (S6), `compat_check.sh`.** Старые тесты на новой схеме:
`git worktree add <scratch>/compat <прошлый тег>`, в нём `server/migrations/*.sql` заменить файлами HEAD,
`DATABASE_URL=…/ruware_hr_compat_test`, `qa-test pytest` из `<worktree>/server` (там `pythonpath` берёт старый код);
venv — HEAD, при другом `requirements.txt` — временный venv прошлого тега; `DROP` только для имени на `_compat_test`. Фикстура прошлой версии (`conftest.py:29–37`) сама
пересоздаёт схемы и своим `db.migrate()` накатывает миграции HEAD — код и тесты N-1 идут на схеме N, включая запись.
Законные падения (тест знает список миграций или значения настроек, `test_migrate.py:37`) — `server/tests/compat_skip.txt`
в HEAD (`nodeid  причина`) → `--deselect`. После — `DROP DATABASE`, `git worktree remove`; venv — HEAD, если
`requirements.txt` совпадает. Цена: если HEAD-миграции потребуют нового `migrate()`, способ надо пересмотреть.

**Данные — `009_release.sql`** (только добавляет):
- `ops.release(id bigserial PK, kind text CHECK (kind IN ('update','auto_rollback','rollback','baseline')),
  from_version text, to_version text NOT NULL, git_commit text, migrations text[] NOT NULL DEFAULT '{}', actor text,
  started_at timestamptz NOT NULL DEFAULT now(), finished_at timestamptz, ok boolean, note text)`, индекс `(started_at DESC)`.
- `ops.release_notice(id bigserial PK, migration text NOT NULL, setting text, message text NOT NULL, created_at …)`.
- `ops.change_default(p_migration, p_key, p_old jsonb, p_new jsonb, p_note) RETURNS boolean` (S8): `UPDATE settings` при
  `value = p_old` и если нет `agent_change` с `after->>'setting' = p_key AND applied_by IS NOT NULL` → запись
  `agent_change` (`kind 'threshold'`, `applied_by NULL`, note «выпуск …»); иначе — `release_notice` «настройка X
  оставлена как есть». Признак «поменяно человеком» отдельным полем не нужен: единственный путь портала —
  `learning.py:283–287`, он пишет `applied_by`; ручной SQL ловит сравнение с прежним значением. Цена: настройку, которую
  человек вписал SQL-ом (так пишет и `scripts/trial_hh.py:74`) ровно равной старому умолчанию, перетрём — с записью в
  `agent_change`. Ключа нет в `settings` — вставка нового значения.

**Линтер миграций (S6)** — тела функций `$$…$$` не проверяются; файл без строки `-- contract: <причина>` падает на: `DROP`, `RENAME`, `ALTER COLUMN … TYPE`,
`SET NOT NULL`, `ADD COLUMN … NOT NULL` без `DEFAULT`, `ADD CONSTRAINT` (CHECK/UNIQUE/FK), `CREATE UNIQUE INDEX`,
`DELETE`, `TRUNCATE`, `UPDATE settings` (только `ops.change_default`). Новые настройки — `ON CONFLICT DO NOTHING`;
`ALTER TYPE … ADD VALUE IF NOT EXISTS` разрешён. Ослабление (комментарий 200→100: `DROP CONSTRAINT` + новый CHECK) —
с пометкой `contract:` и строкой в «Миграции» CHANGELOG; старый код проверяет 200 сам, откат возможен.

**S11, первый переход.** Клон рядом с установкой (`ssh` по deploy key), `git checkout v1.0.0`;
`diff -r` с установкой без `.git`, `.env`, `data/`, `.venv`, `__pycache__` — расхождения печатаются, при любых —
стоп и решение человека. Затем перенос `.env`, `server/data`, `update.conf`, `server/.venv` → `server/.venvs/v1.0.0` + симлинк
`server/.venv`, переименование каталогов (старый → `*-zip`, клон → прежнее имя) — пути служб и шебанги venv не меняются. У v1.0.0 нет `hr.cli version`: проверка S11 —
`git describe --tags` = v1.0.0 и чистый `git status`; запись `baseline` в `ops.release` делает первый `update.sh`.

**Внешние сервисы.** GitHub по SSH: `ConnectTimeout=20`, `BatchMode=yes`; отказ — стоп на шаге 1, портал не тронут.
PyPI: `UV_HTTP_TIMEOUT=60`, отказ — стоп на шаге 3. Повторов нет: инженер перезапускает команду, шаги идемпотентны.

## Безопасность — backend-architect

- **Данные.** Копия базы — все ПДн, включая `raw` с контактами (AD-3, уточнение 2026-10-25): `BACKUP_DIR` вне
  репозитория, каталог 700, файл 600 (`umask 077`), владелец — пользователь служб, не в синхронизируемых и общих
  папках; копия одна (S12), восстановление вручную.
- **Секреты.** Скрипты `.env` не выполняют и значений не печатают; `env-missing` читает только имена ключей и
  непустоту; `set -x` запрещён; в `ops.release.note` и итоге — без значений. `update.conf` — исполняемые команды:
  600, владелец тот же, считается кодом установки.
- **Доступ к GitHub.** Deploy key только на чтение, свой на сервер, ed25519, файл 600, `IdentitiesOnly`; ключ хоста
  GitHub — в `known_hosts` по опубликованным отпечаткам, `StrictHostKeyChecking=yes`. Агент ключа и доступа к рабочему
  серверу не получает (security.md п.1); тег на GitHub ставит агент, ставит на сервер — инженер.
- **Происхождение тега.** SSH + закреплённый ключ хоста + deploy key; `update.sh` печатает коммит тега,
  `ops.release.git_commit` его хранит; локальный тег без `--force` не переписывается. Не защищает от взлома учётной
  записи с правом записи в репозиторий — принято, см. «Решения».
- **Недоверенный ввод** почти отсутствует: аргумент-тег (шаблон до использования, всюду в кавычках) и `update.conf`
  (владелец — инженер). `exec` скрипта из тега доверяет ему не больше, чем ставимому коду.
- **Точки входа.** `GET /api/version` без входа: только номер и дата, без путей, настроек и состояния базы; доступен
  лишь через туннель/внутренний прокси (AD-6). Остальное — CLI на сервере.
- **Зависимости.** `release.sh` гоняет `pip-audit` (security.md п.5); на сервере ставятся закреплённые версии
  `requirements.txt`.
- **MITRE ATLAS / LLM.** Фича не касается модели и её данных — неприменимо.
