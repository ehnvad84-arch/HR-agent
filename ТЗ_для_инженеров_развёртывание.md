# Техническое задание: развернуть систему агента подбора персонала

**Внутренний документ.** Версия 1.1 от 26.09.2026. Исполнитель — инженерная
служба или подрядчик. Заказчик — отдел персонала «Рувер».

Документ рассчитан на инженера, который системы не видел и в контекст не
погружён. Всё, что нужно для запуска, здесь: состав стека, команды,
переменные окружения, куда вносить учётные данные, как подключить любую
языковую модель, какие сервисы сбора включать и как принимать работу.

Сопутствующие файлы, лежат в этой же папке:

| Файл | Зачем |
|---|---|
| `Агент_подбора_архитектура_v1.1.md` | что за система, какие источники, как считается балл |
| `schema_recruiting.sql` | схема базы, разворачивается как есть |
| `Рабочее_место_рекрутера.html` | прототип интерфейса, служит эталоном экранов и поведения |
| `Мануал_рекрутера.md` | как этим пользуется заказчик — читать, чтобы понимать, что важно |

## 0. Что должно получиться

Работающий контур на арендованном сервере, который каждое утро сам собирает
резюме с площадок, сравнивает их с профилями 83 должностей, находит изменения в
резюме тех, за кем наблюдает, и показывает рекрутеру короткий список людей с
объяснением, почему они попали в список. Все действия, касающиеся людей, агент
готовит, но не выполняет: письмо уходит после нажатия человеком.

Ничего из этого не требует учётной записи директора. Сервер, домен, почтовый
ящик подбора, аккаунт работодателя на площадках и ключи к языковой модели
оформляются на компанию и передаются инженерной службе. Список того, что нужно
получить у заказчика до начала работ, — в разделе 4.

## 1. Сервер и окружение

### 1.1. Требования

| Параметр | Значение | Почему столько |
|---|---|---|
| CPU | 4 ядра | обход площадок и скоринг идут параллельно по 6–11 запросам |
| RAM | 8 ГБ | PostgreSQL с pgvector, n8n, API, служебные контейнеры |
| Диск | 80 ГБ SSD | база с историей версий резюме растёт примерно на 1,5 ГБ в год при 5 000 наблюдений |
| ОС | Ubuntu 22.04 LTS или 24.04 LTS | |
| Сеть | статический IP, домен, 443 наружу | интерфейс рекрутеров и вебхуки n8n |
| Провайдер | любой: Timeweb Cloud, Selectel, Cloud.ru, свой сервер | привязки к конкретному провайдеру в системе нет |

Если языковая модель поднимается локально (раздел 6, вариант В), нужен
отдельный сервер с GPU от 24 ГБ видеопамяти. При работе через облачный доступ
к модели дополнительного железа не нужно.

### 1.2. Подготовка сервера

```bash
# пользователь без root, ключи, брандмауэр
adduser ruware && usermod -aG sudo ruware
rsync --archive --chown=ruware:ruware ~/.ssh /home/ruware
ufw allow OpenSSH && ufw allow 80 && ufw allow 443 && ufw enable
sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
systemctl restart ssh

# docker
curl -fsSL https://get.docker.com | sh
usermod -aG docker ruware
```

## 2. Состав контура

```
                    ┌──────────────── nginx (443, TLS) ────────────────┐
                    │                                                  │
              web (интерфейс рекрутера)            n8n (пайплайны, 5678 внутри)
                    │                                                  │
                    └──────────────── api (FastAPI) ───────────────────┘
                                       │          │
                             PostgreSQL 16        MinIO или S3 провайдера
                             + pgvector           (файлы резюме)
                             + pg_trgm
                                       │
                                  LLM-шлюз (внешний или локальный)
```

Семь контейнеров: `db`, `api`, `web`, `n8n`, `storage`, `bot`, `stt`. Восьмой,
`ollama`, — только если модель поднимается локально. `bot` — телеграм-бот
руководителей, `stt` — расшифровка голоса внутри контура (раздел 10а).

Разделение ответственности: n8n держит расписания, коннекторы к площадкам и
ретраи; `api` — вся бизнес-логика (дедупликация, скоринг, статусы, очередь
действий) и единственный, кто пишет в базу; `web` — статика интерфейса.
Так сделано, чтобы логику можно было тестировать без n8n, а расписания менять
без выкладки кода.

### 2.1. docker-compose.yml

```yaml
services:
  db:
    image: pgvector/pgvector:pg16
    environment:
      POSTGRES_DB: ruware_hr
      POSTGRES_USER: ${DB_USER}
      POSTGRES_PASSWORD: ${DB_PASSWORD}
    volumes:
      - ./data/db:/var/lib/postgresql/data
      - ./schema_recruiting.sql:/docker-entrypoint-initdb.d/10-schema.sql:ro
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U ${DB_USER} -d ruware_hr"]
      interval: 10s
    restart: unless-stopped

  api:
    build: ./api
    env_file: .env
    depends_on:
      db: {condition: service_healthy}
    restart: unless-stopped

  web:
    build: ./web
    depends_on: [api]
    restart: unless-stopped

  n8n:
    image: n8nio/n8n:latest
    env_file: .env
    environment:
      N8N_HOST: ${DOMAIN}
      WEBHOOK_URL: https://${DOMAIN}/n8n/
      GENERIC_TIMEZONE: Europe/Moscow
      N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}
    volumes:
      - ./data/n8n:/home/node/.n8n
    depends_on:
      db: {condition: service_healthy}
    restart: unless-stopped

  storage:
    image: minio/minio:latest
    command: server /data --console-address ":9001"
    environment:
      MINIO_ROOT_USER: ${S3_KEY}
      MINIO_ROOT_PASSWORD: ${S3_SECRET}
    volumes:
      - ./data/minio:/data
    restart: unless-stopped

  bot:
    build: ./bot            # aiogram; вся логика — через api, в базу бот не пишет
    env_file: .env
    depends_on: [api, stt]
    restart: unless-stopped

  stt:
    build: ./stt            # faster-whisper, модель из STT_MODEL; наружу порт не открыт
    env_file: .env
    volumes:
      - ./data/stt-models:/models
    restart: unless-stopped

  proxy:
    image: nginx:alpine
    ports: ["80:80", "443:443"]
    volumes:
      - ./nginx.conf:/etc/nginx/nginx.conf:ro
      - ./certs:/etc/letsencrypt:ro
    depends_on: [web, api, n8n]
    restart: unless-stopped
```

Если объектное хранилище провайдера дешевле и надёжнее собственного MinIO —
берите его: в коде это адрес, ключ и бакет, контейнер `storage` тогда не нужен.

## 3. Порядок развёртывания

```bash
git clone <репозиторий> /opt/ruware-hr && cd /opt/ruware-hr
cp .env.example .env && nano .env          # раздел 4 и 5 этого документа
docker compose up -d db                     # схема накатится сама из schema_recruiting.sql
docker compose exec db psql -U $DB_USER -d ruware_hr -c '\dt'   # должно быть 37 таблиц
python scripts/seed_departments.py          # справочник подразделений
python scripts/import_di.py --src "/opt/ruware-hr/di/" --dry-run   # разбор 83 ДИ, см. раздел 8
docker compose up -d                        # весь контур
docker compose logs -f api | head -50
```

Проверка после старта:

```bash
curl -fsS https://$DOMAIN/api/health                 # {"status":"ok","db":"ok","llm":"ok"}
curl -fsS https://$DOMAIN/api/sources | jq '.[].code'  # hh, trudvsem, avito, habr, manual
```

## 5. Учётные данные: куда что вносить

Все секреты живут в двух местах и больше нигде: файл `.env` на сервере (права
`600`, владелец `ruware`) и хранилище учётных данных n8n, зашифрованное ключом
`N8N_ENCRYPTION_KEY`. В репозиторий, в код и в переписку секреты не попадают.

### 5.1. Файл `.env`

```bash
# --- контур
DOMAIN=hr.example.ru
TZ=Europe/Moscow

# --- база
DB_USER=ruware
DB_PASSWORD=<сгенерировать: openssl rand -base64 24>
DATABASE_URL=postgresql://ruware:<пароль>@db:5432/ruware_hr

# --- объектное хранилище (MinIO или S3 провайдера)
S3_ENDPOINT=http://storage:9000
S3_KEY=<ключ>
S3_SECRET=<секрет>
S3_BUCKET=resumes

# --- языковая модель: любой провайдер с OpenAI-совместимым интерфейсом
LLM_BASE_URL=https://<адрес-шлюза>/v1
LLM_API_KEY=<ключ>
LLM_MODEL=<имя модели>
LLM_TEMPERATURE=0.1
LLM_MAX_TOKENS=4096
LLM_TIMEOUT_S=90

# --- hh.ru: приложение работодателя, см. 5.2
HH_CLIENT_ID=<из кабинета разработчика>
HH_CLIENT_SECRET=<из кабинета разработчика>
HH_REFRESH_TOKEN=<получается один раз по OAuth>
HH_EMPLOYER_ID=<идентификатор компании>
HH_USER_AGENT="RuwareHR/1.0 (hr@example.ru)"

# --- Работа России: открытые данные, ключ не нужен
TRUDVSEM_BASE=https://opendata.trudvsem.ru/api/v1/integration

# --- Авито Работа (если подключается)
AVITO_CLIENT_ID=
AVITO_CLIENT_SECRET=

# --- почта ящика подбора
SMTP_HOST=smtp.example.ru
SMTP_PORT=587
SMTP_USER=hr@example.ru
SMTP_PASSWORD=<пароль приложения>
IMAP_HOST=imap.example.ru
DIGEST_TO=hr@example.ru,head-hr@example.ru

# --- телеграм-бот для служебных уведомлений (падение обхода)
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=

# --- телеграм-бот руководителей, раздел 10а (отдельный бот, не служебный)
MANAGER_BOT_TOKEN=
STT_URL=http://stt:8000
STT_MODEL=medium            # large-v3, если на сервере есть GPU

# --- профессиональные следы в сети, раздел 7.2 (пусто = источник выключен)
GITHUB_TOKEN=            # обычный personal access token, нужен только ради лимитов
VK_SERVICE_TOKEN=        # сервисный ключ приложения ВК, доступ к открытым профилям
TGSTAT_TOKEN=            # поиск профильных каналов и чатов по региону и теме

# --- сервисы сбора со страниц, раздел 7 (пусто = выключено)
FIRECRAWL_BASE_URL=
FIRECRAWL_API_KEY=
PLAYWRIGHT_MCP_URL=

# --- служебное
N8N_ENCRYPTION_KEY=<openssl rand -hex 32>
JWT_SECRET=<openssl rand -hex 32>
```

### 5.2. hh.ru — единственная неочевидная настройка

1. Зайти в кабинет разработчика `dev.hh.ru` под корпоративной учётной записью
   работодателя, создать приложение, указать `redirect_uri`
   `https://<домен>/api/oauth/hh/callback`.
2. Получить `client_id` и `client_secret`, внести в `.env`.
3. Один раз пройти авторизацию менеджером работодателя: открыть
   `https://<домен>/api/oauth/hh/start`, подтвердить доступ, сервис сохранит
   `refresh_token` в `.env` или в таблицу `settings`.
4. Проверить: `curl -fsS https://<домен>/api/sources/hh/selftest` — вернёт число
   доступных резюме по тестовому запросу и остаток квоты контактов.

Ограничения площадки, которые нужно заложить в коннектор: `User-Agent` с
контактом компании обязателен; частота — не чаще одного запроса в секунду;
контакты кандидатов открываются только по действию пользователя и каждый раз
пишутся в `audit_log` с идентификатором рекрутера.

### 5.3. Остальные площадки

`trudvsem` — открытое API, ключей нет, ограничение по частоте мягкое.
`Хабр Карьера` и площадки без API — выгрузка из кабинета в файл, инженер
настраивает папку `import/` на сервере: n8n забирает оттуда файлы по маске
`*.csv`, `*.xlsx` и складывает в `observation` с `source.mode = cabinet_export`.
Авито Работа — API для работодателей по заявке; до одобрения работает та же
файловая схема.

## 6. Языковая модель: как поставить любую

Система обращается к модели через OpenAI-совместимый интерфейс
(`POST {LLM_BASE_URL}/chat/completions`). Это единственная точка интеграции,
поэтому смена провайдера — три переменные в `.env` и перезапуск `api`.

**Вариант А. Облачный доступ через совместимый шлюз.** Работает с любым
провайдером, который отдаёт OpenAI-совместимый эндпойнт, в том числе с
российскими моделями через прослойку совместимости. Заполняются
`LLM_BASE_URL`, `LLM_API_KEY`, `LLM_MODEL`.

**Вариант Б. Провайдер со своим протоколом** (например, GigaChat или YandexGPT
в их родном виде). Пишется адаптер `api/llm/<provider>.py` по интерфейсу
`complete(messages, schema) -> dict`; остальной код не трогается. Переменная
`LLM_PROVIDER=<имя>` переключает реализацию.

**Вариант В. Локальная модель.** `ollama serve` или vLLM на сервере с GPU,
`LLM_BASE_URL=http://ollama:11434/v1`. Требования к модели: русский язык,
контекст от 32 тысяч токенов, устойчивый JSON по схеме. Практически это модель
класса 12–32 млрд параметров в квантовании 4–8 бит. Качество объяснений будет
ниже облачных, на сортировку карточек это влияет мало, на текст письма — заметно.

Что именно поручается модели и что считается кодом:

| Задача | Кто делает | Почему так |
|---|---|---|
| Разбор резюме на поля | код, модель как запасной путь | у площадок структурированный ответ, модель нужна только для свободного текста |
| Признаки для скоринга (стаж, доноры, ключевые слова) | код | должно быть воспроизводимо и проверяемо |
| Балл | код по весам профиля | чтобы можно было объяснить и пересчитать |
| Объяснение балла, вопросы для скрининга | модель | здесь нужен язык, а не арифметика |
| Текст первого письма | модель по шаблону | всегда уходит человеку на подтверждение |
| Решение написать, отказать, пригласить | человек | требование заказчика, пункт 4.2 опросника |

Промпты хранятся в таблице `agent_prompt` с версиями и флагом активности:
менять текст промпта можно без выкладки кода. Температура по умолчанию 0,1.

## 7. Сбор данных и MCP-сервисы

Порядок предпочтения жёсткий: **официальное API → выгрузка из кабинета →
сбор со страниц**. Первые два способа покрывают hh и «Работу России», то есть
основной объём. Третий включается только там, где первых двух нет.

### 7.1. Если сбор со страниц включается

Решение принято заказчиком 26.09.2026. Техническая сторона:

| Сервис | Когда нужен | Как подключить |
|---|---|---|
| **Playwright MCP** (`@playwright/mcp`) | страницы за авторизацией: кабинет площадки, где нет выгрузки | контейнер рядом с n8n, адрес в `PLAYWRIGHT_MCP_URL`; работает под аккаунтом компании, сессия хранится в томе |
| **Firecrawl MCP** (облако или self-hosted) | публичные страницы и списки, когда нужен готовый текст вместо HTML | `FIRECRAWL_BASE_URL`, `FIRECRAWL_API_KEY`; self-hosted снимает вопрос передачи данных наружу |
| Свой коннектор на `httpx` + `selectolax` | простые страницы со стабильной разметкой | дешевле и быстрее MCP, но ломается при смене вёрстки |

Ограничения, которые вносятся в конфигурацию коннектора и не обсуждаются:
не чаще 1 запроса в секунду на площадку и не больше 2000 страниц за ночной
прогон; обход идёт с серверного IP под корпоративным аккаунтом, без ротации
адресов и без обхода защиты от роботов — если площадка показывает проверку,
задача останавливается и в журнал пишется причина. Обходить капчу, подменять
отпечаток браузера и прятать источник запросов не нужно и не делаем: такой
контур ломается на первом же обновлении площадки и стоит компании оплаченного
доступа к hh.

### 7.2. Профессиональные следы в сети

Требование заказчика от 26.09.2026: по каждому человеку в базе агент ищет его
профессиональные профили и прикладывает к досье.

| Источник | Как берём | Что кладём в `social_profile` |
|---|---|---|
| GitHub, GitLab | официальное API, поиск по нику, почте, имени и компании | язык, число репозиториев, дата последнего коммита, описание активности |
| ВКонтакте, Одноклассники | API открытых данных по запросу «имя + город + работодатель» | город, место работы, профессиональные публикации |
| Telegram | поиск каналов и чатов через TGStat по региону и теме, чтение открытых сообщений | ник, темы, уровень ответов; личные переписки недоступны и не нужны |
| LinkedIn | публичные страницы профилей через общий поиск; собственного доступа к площадке нет | опыт, работодатели, специализация |
| Facebook, Instagram | только открытые профили, найденные общедоступным поиском; доступ к площадкам не настраивается | место работы, профессиональные публикации |
| X, YouTube, Дзен | публичные страницы и открытые API, где они есть | посты, доклады, разборы по специальности |
| Хабр Карьера, форумы, конференции | кабинет либо Firecrawl MCP по публичной странице | профиль, статьи, ответы, доклады |

Список площадок — настройка `social_sources`, а не константа в коде: добавление площадки не
требует выкладки. По каждой площадке из списка пишется результат, включая отрицательный
(`social_search`): какие запросы пробовали, нашли или нет, было ли ограничение доступа.

**Поиск имени идёт в двух алфавитах.** Модуль поиска строит варианты: транслитерация фамилии и
имени, прямой и обратный порядок, написание через точку и подчёркивание, частые пары
(`iu`/`yu`, `ia`/`ya`, `ii`/`y`), плюс ник из резюме и других профилей, почта, телефон,
работодатель. Варианты сохраняются в `person.name_variants`, чтобы поиск был воспроизводим и
чтобы по ним же можно было искать повторно.

Правила, которые пишутся в код, а не в инструкцию:

- Совпадение оценивается по набору признаков (имя, работодатель, город, почта,
  ник). Полное совпадение — `confidence = confirmed`, частичное — `probable`.
  `probable` не показывается как факт: рекрутер подтверждает его кнопкой, и
  только после этого профиль считается принадлежащим человеку.
- В `summary` пишется только профессиональное: стек, активность, экспертиза.
  Личная жизнь, взгляды, фотографии, круг общения не извлекаются и не хранятся.
- Закрытые профили не трогаем: авторизация под чужим именем, запросы в друзья и
  обход приватности не предусмотрены ни в одном сценарии.
- Частота та же, что у площадок: не чаще запроса в секунду на источник; поиск
  следов идёт ночным прогоном, а не в утреннем окне.

### 7.2а. Обмен с 1С: заявки на подбор

Заявки заводятся и согласовываются в 1С. Система их только читает, встречной
записи нет. Механизм — тот же, что принят в проекте по безопасности 1С: выгрузка
файлом на чтение, без прямого подключения к базе.

Порядок: обработка в 1С по расписанию кладёт в обменный каталог файл с полями
«идентификатор заявки, подразделение, должность, число ставок, причина, срок,
заказчик, кто согласовал, дата согласования, номер черновика из бота»; воркфлоу `requests_from_1c`
забирает файл в 06:20, сверяет по идентификатору, новые заявки заводит,
изменившиеся обновляет, по согласованным создаёт вакансию с
`origin = request_1c`. Строка выгрузки сохраняется в `vacancy_request.raw`
целиком, чтобы расхождения можно было разобрать без 1С.

Что нужно от стороны 1С: состав полей и формат (CSV или JSON), каталог обмена и
расписание выгрузки. Это предмет отдельной настройки, до неё вакансии заводятся
рекрутером вручную — система от обмена не зависит.

Если в строке заявки есть идентификатор позиции штатного расписания, он
сохраняется в `vacancy_request.staff_position_id` и переходит в вакансию (раздел 7.2б).

Если есть номер черновика из бота (раздел 10а), заявка связывается с
`request_draft`: черновик переходит в `linked`, а вакансия получает его критерии и
людей с отметкой «нравится». Номер, которого нет в базе, не ломает приём: заявка
заводится, а расхождение уходит руководителю отдела персонала.

### 7.2б. Обмен с 1С:ERP: оргструктура и штатное расписание

Назначение и правила — раздел 3.9 архитектуры. Механизм тот же, что в 7.2а:
файл на чтение в том же обменном каталоге, встречной записи в 1С нет.

**Что выгружает 1С.** Обработка в 1С:ERP каждые 30 минут в рабочее время кладёт
файл `orgstructure_<ГГГГММДД-ЧЧММСС>.json`. Это полный снимок, а не дельта:

```json
{
  "exported_at": "2026-10-24T09:30:00+03:00",
  "units": [
    {"id": "<guid>", "parent_id": null, "organization": "<юрлицо>", "code": "00-000001",
     "title": "Коммерческая служба", "closed": false}
  ],
  "positions": [
    {"id": "<guid>", "unit_id": "<guid>", "job_id": "<guid>", "job_title": "Менеджер по продажам",
     "rates_total": 3, "rates_occupied": 2, "valid_from": "2026-01-01", "closed": false}
  ],
  "counts": {"units": 1, "positions": 1}
}
```

Источник в 1С:ERP: справочники подразделений и должностей, позиции штатного
расписания и данные об их занятости. ФИО сотрудников в файл не входят. Если
штатное расписание в ERP не ведётся, состав полей согласуется с 1С-специалистами
отдельно (вопрос 11 раздела 9 архитектуры).

**Что делает воркфлоу `orgstructure_from_1c`.** Проверяет каталог каждые 10
минут и берёт самый свежий необработанный файл; более старые помечает `outdated`.

1. Считает `sha256`; если такой файл уже был — пропускает.
2. Проверяет файл: JSON по схеме, `counts` сходятся, у каждого `parent_id` и
   `unit_id` есть пара в этом же файле, `exported_at` новее последнего
   применённого, ставки не отрицательные, доля пропавших позиций не больше
   `org_max_drop_pct`. При любой ошибке — `org_sync.state = rejected` с текстом в
   `error`, сообщение в служебный телеграм, данные не трогаются.
3. В одной транзакции сверяет снимок с `org_unit` и `staff_position` по
   внешним идентификаторам: новые заводит, изменившиеся обновляет, исчезнувшие
   помечает `is_active = false`. Ничего не удаляет. Каждое отличие пишет в
   `org_change`. Строку файла сохраняет в `staff_position.raw`.
4. Новые должности, которых нет в `job_role_map`, ставит в очередь «Не
   сопоставлено» — это уведомление руководителю отдела персонала.
5. По событиям `org_change` формирует уведомления рекрутерам: открылась ставка —
   список подходящих по сопоставленному профилю; закрыли позицию с открытой
   вакансией — предупреждение. Вакансии сам не создаёт и не закрывает.

`watchdog` дополнительно проверяет, что последний применённый снимок не старше
`org_sync_stale_hours`, иначе пишет в телеграм.

**Порядок первого запуска.** Первая выгрузка применяется без порога
`org_max_drop_pct` (сравнивать не с чем). Сразу после неё руководитель отдела
персонала сопоставляет подразделения с функциональными группами и должности с
профилями на экране «Оргструктура». Пока сопоставления нет, система показывает
ставки, но не подбирает под них людей.

Что нужно от стороны 1С: обработка выгрузки по формату выше, расписание, ответ
на вопрос 11 раздела 9 архитектуры. До настройки обмена экран «Оргструктура»
пуст, остальная система работает как прежде.

### 7.3. Хранение сырых ответов

Данные, полученные любым способом, складываются в `observation.raw` и в
`obs_version` целиком — это позволяет пересчитывать оценки, не обращаясь к
площадке повторно, и снижает число запросов на порядок.

## 9. Импорт должностных инструкций в профили ролей

83 файла `.docx` лежат в каталоге `ДИ с правками по КТ от 25 сент. 2026`.

```bash
python scripts/import_di.py --src "./di" --out profiles.json --dry-run
python scripts/import_di.py --src "./di" --apply --approve-by <user_id>
```

Что делает скрипт: конвертирует `.docx` в текст, отдаёт модели вместе со схемой
профиля, получает JSON (обязательные требования, желательные, инструменты,
образование, подчинённость), сверяет с шаблоном и пишет в `role_profile` со
статусом «черновик». Веса, компании-доноры, вилка и география проставляются
рекрутером в интерфейсе — из ДИ они не выводятся.

Правило: профиль не участвует в скоринге, пока у него не проставлены
`approved_by` и `approved_at`. Черновик, попавший в работу, даёт поток
нерелевантных карточек и убивает доверие к системе за неделю.

## 10. Интерфейс

Эталон — `Рабочее_место_рекрутера.html`. Это не картинка: там рабочая разметка,
поведение кнопок, состав полей и тексты. Реализовать восемь экранов: «Сегодня»,
досье кандидата (резюме, следы в сети, разбор балла, лента изменений), база с
сортировкой по любой колонке и фильтрами по значениям, вакансии и заявки,
профили должностей со списком всех 83 ролей и предпросмотром изменений, обучение
агента (чат плюс недельная сводка с анкетой для руководителя), воронка, схема
работы агента. Сверх прототипа: экран «Оргструктура» (раздел 5.3г архитектуры),
а на экране вакансий — вкладки «Черновики из бота» и «Доступ к боту» для
руководителя отдела персонала (раздел 10а). Нанимающему руководителю база и
досье доступны на чтение, кнопки решений и открытия контактов ему не показываются.

Два правила интерфейса, которые нельзя обойти: решения «отложить» и «не наш»
требуют комментария не короче 200 знаков (проверка дублируется в СУБД), а правка
профиля создаёт новую версию и не влияет на выдачу до утверждения.

Минимальный набор эндпойнтов:

Аутентификация: пользователи приходят из 1С, своих учётных записей система не создаёт.

Порядок: обработка в 1С кладёт в обменный каталог выгрузку сотрудников отдела персонала и

руководитель» и нужны для подтверждения доступа к боту (раздел 10а); воркфлоу
`users_from_1c` забирает её ежедневно, заводит новых, обновляет изменившихся и снимает
`is_active` у уволенных. Роль подставляется по должности по таблице соответствия и дальше
правится руководителем отдела персонала.

Способ входа выбирается вместе с 1С-специалистами компании, оба варианта поддерживаются кодом:

1. **Единый вход** через сервис аутентификации на стороне 1С (OIDC или аналог): система проверяет
   токен и не хранит паролей вообще. Предпочтительный вариант.
2. **Выгрузка пользователей плюс пароль в системе**: логин тот же, что в 1С, пароль задаётся при
   первом входе и хранится хешем. Работает без участия 1С-специалистов, поэтому включается первым.

Права — по матрице `role_permission`, её читают и интерфейс, и API; права проверяются на сервере,
интерфейс только прячет недоступное. Открытие контакта и выгрузка досье пишутся в `audit_log`
всегда, без исключений для администраторов.

Контур арендуется у Timeweb на компанию: сервер, объектное хранилище, домен. Доступ к серверу — по
ключам двух инженеров компании, root-вход отключён.

## 10а. Телеграм-бот руководителей

Назначение и правила — раздел 3.10 архитектуры. Главное для реализации: бот
готовит **черновик**, а заявка заводится и согласуется в 1С. Кнопки «утвердить
заявку» в боте нет и быть не должно.

**Устройство.** Контейнер `bot` (aiogram, long polling, без входящего порта)
ходит только в `api` и в `stt`. Вся логика — состояния черновика, подбор,
пересчёт критериев — живёт в `api`, как и остальная бизнес-логика (раздел 2).
Бот регистрируется в BotFather на корпоративный аккаунт, токен — `MANAGER_BOT_TOKEN`.
Это отдельный бот, служебный `TELEGRAM_BOT_TOKEN` для него не используется.

**Доступ.** `/start` создаёт `tg_access_request`. Руководитель отдела персонала
на вкладке «Доступ к боту» выбирает сотрудника из `app_user` с ролью
`hiring_manager` и подтверждает — в `app_user.telegram_id` записывается
идентификатор. Каждое сообщение бот проверяет по `telegram_id` и `is_active`.
Уволенный в 1С теряет доступ после ближайшей выгрузки `users_from_1c`.

**Голос.** Бот скачивает голосовое сообщение, отдаёт его в `stt`
(`POST {STT_URL}/transcribe`, русский язык) и удаляет файл после расшифровки.
Хранится только текст — в `request_draft_message`. Голос во внешние сервисы
распознавания не отправляется.

**Черновик.** Из текста модель (раздел 6) извлекает поля черновика по
JSON-схеме: должность, число ставок, срок, причина, вилка, требования. Должность
сопоставляется с профилем через `job_role_map` и базу должностей. Открытые
позиции подразделения руководителя берутся из `v_open_positions` по
`app_user.org_unit_id` и предлагаются кнопками. Номер черновика выдаётся при
создании: `Ч-<год>-<порядковый>`.

**Подборка и уточнение.** Балл считается тем же кодом скоринга (раздел 6:
балл — код, не модель) по профилю с наложенными `request_draft.criteria`. Бот
присылает карточки прямо в чат, по сообщению на человека. В карточке: ярлык,
город, опыт, навыки, балл и его разбор. Под карточкой кнопки «нравится»,
«не нравится» и «подробнее». «Подробнее» присылает досье в том объёме, который
видит рекрутер, без контактов. Ответы «нравится / не нравится» с причиной
пишутся в `draft_candidate`. Модель по причинам предлагает правку `criteria`,
правка применяется только после подтверждения руководителем, затем считается
следующий раунд (`round + 1`).

**Поиск по базе.** Роль `hiring_manager` имеет `base.read`: руководитель ищет
по всей базе и в боте (команда `/найти` или голосом), и в рабочем месте. Нет у
него `person.take`, открытия контактов, решений по людям и отправки писем —
`api` отвечает отказом. Каждый показ карточки руководителю, в боте или в
интерфейсе, пишется в `audit_log` с `action = view` и каналом.

**Отправка и проверка.** «Отправить в отдел персонала» переводит черновик в
`submitted`, руководителю отдела персонала — уведомление. На вкладке «Черновики
из бота» он видит черновик, переписку и отмеченных людей и выбирает «вернуть»
(обязательный комментарий) или «готов к 1С». После «готов к 1С» бот присылает
руководителю текст заявки и номер черновика для поля в 1С. Связка с заявкой —
раздел 7.2а.

**Что передаётся через Telegram.** Решение заказчика от 24.10.2026: текст
черновика, номер, уведомления и карточки кандидатов, включая досье. Контакты
кандидатов не передаются никогда. Запускать бот можно после ответа юриста на
вопрос 13 раздела 9 архитектуры (трансграничная передача).

## 11. Резервное копирование и восстановление

```bash
# ежедневно в 03:00, хранение 30 дней
docker compose exec -T db pg_dump -U $DB_USER ruware_hr | gzip > /backup/hr_$(date +%F).sql.gz
find /backup -name 'hr_*.sql.gz' -mtime +30 -delete
```

Раз в месяц — проверка восстановления на отдельной машине: разворачивается
последний дамп, запускается `api`, открывается карточка. Бэкап, который ни разу
не восстанавливали, бэкапом не считается. Файлы резюме из объектного хранилища
копируются отдельно (`mc mirror` или средства провайдера).
