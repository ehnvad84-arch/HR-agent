# Обновление портала подбора «Рувер»

Для инженера, который обслуживает портал на сервере компании. Версия от 23.11.2026, для v1.1.0 и новее.
Переход на v1.2.0 (поиск по смыслу) — раздел 7: до обновления нужна служба векторов bge-m3.
Переход на v1.3.0 (воронка по этапам) — раздел 8: обычное обновление, новых служб и переменных нет.
Шаги проверены репетицией на пробном сервере: установка v1.0.0 из архива → переход → обновления → отказы →
откат. Установка с нуля — `УСТАНОВКА_на_сервер.md`, что нового в каждой версии — `CHANGELOG.md`.

Ниже каталог установки — `~/projects/HR-agent` (как в инструкции по установке), команды — от пользователя,
под которым работают службы портала. Ключи и пароли из `.env` никуда не пересылаются и в чаты не вставляются.

## 1. Как устроено

- Каждая версия — тег `vX.Y.Z` в репозитории GitHub: Z — исправления, Y — новые возможности, X — несовместимые
  изменения. Номер работающей версии — внизу «Схемы» → «Как работает портал» и по адресу `/api/version`.
- Установка — копия репозитория на теге. Сервер берёт версии ключом GitHub **только на чтение**; агент
  разработки доступа к серверу не имеет.
- Обновление — одна команда `update.sh`: проверки, пока портал работает → остановка → копия базы → код,
  зависимости, миграции → запуск и проверка. Не прошло — портал сам возвращается на прежнюю версию.
- Миграции только добавляют: прошлая версия работает на базе новой. Поэтому откат (`rollback.sh`) меняет
  только код, базу не трогает, и всё, что рекрутеры сделали после обновления, остаётся.
- На каждую версию — свой каталог зависимостей `server/.venvs/<тег>`, `server/.venv` — ссылка на текущий.
  Хранятся текущий и прошлый: откат идёт за секунды и без интернета.
- Копия базы на сервере одна и свежая: пишется раз в неделю таймером и перед каждым обновлением с
  миграциями. Новая заменяет прежнюю только после проверки.

Портал на время обновления недоступен несколько минут: обновляйте вечером или до 8:00, не в 18:00 (сбор hh).

## 2. Первый раз: установка из архива становится копией репозитория

Нужен один раз на сервере, где v1.0.0 стоит из ZIP-архива (без каталога `.git`). Службы, база, `.env` и
файлы в `server/data` не меняются; пути служб и программ тоже.

### 2.1. Ключ GitHub только на чтение

```bash
ssh-keygen -t ed25519 -N "" -C "ruware-<имя сервера>" -f ~/.ssh/ruware_github
chmod 600 ~/.ssh/ruware_github
cat ~/.ssh/ruware_github.pub
```

Строку `ssh-ed25519 AAAA…` отправьте владельцу репозитория: он добавит её в Settings → Deploy keys **без**
«Allow write access». Закрытый ключ (`ruware_github` без `.pub`) с сервера не уходит.

В `~/.ssh/config` (права 600):

```
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/ruware_github
  IdentitiesOnly yes
  StrictHostKeyChecking yes
```

Ключ сервера GitHub — в `~/.ssh/known_hosts`, сверенный с опубликованным отпечатком:

```bash
ssh-keyscan -t ed25519 github.com > /tmp/gh.key && ssh-keygen -lf /tmp/gh.key
# отпечаток обязан совпасть с SHA256 для ED25519 на странице
# https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints
cat /tmp/gh.key >> ~/.ssh/known_hosts && rm /tmp/gh.key
ssh -T git@github.com    # «Hi ehnvad84-arch/HR-agent! You've successfully authenticated…» — ключ работает
```

Не совпал отпечаток — дальше не идите, сообщите владельцу репозитория.

### 2.6. Настройки обновления `server/update.conf`

Образца у v1.0.0 нет — берётся из тега v1.1.0:

```bash
cd ~/projects/HR-agent
git fetch --tags origin
(umask 077; git show v1.1.0:server/update.conf.example > server/update.conf)
nano server/update.conf
```

Заполните: `STOP_CMD` и `START_CMD` (таймеры и портал, как у вас устроено: образец — systemd пользователя,
второй вариант — системная служба и cron), `BACKUP_DIR` — каталог копии базы **вне** репозитория и не в общих
папках (в копии все персональные данные), `PG_DUMP` — pg_dump 16 с вашей базой (на сервере или
`docker exec …`), пароль базы — в `~/.pgpass` (600), не в этом файле. Файл — 600: в нём исполняемые команды.

### 2.8. Недельный таймер копии базы

Образец юнитов — в конце `server/update.conf.example` (`ruware-db-copy.service` и `.timer`, воскресенье 03:00).
Поправьте в нём `WorkingDirectory` на каталог установки, положите файлы в `~/.config/systemd/user/` и

```bash

```

## 3. Обычное обновление

Номер новой версии и её «Ручные шаги» — в `CHANGELOG.md` (`git fetch --tags origin && git show
vX.Y.Z:CHANGELOG.md | head -40`).

```bash
cd ~/projects/HR-agent
tmux new -A -s update     # обрыв SSH не прервёт обновление; вернуться — та же команда
bash server/scripts/update.sh v1.2.0
```

Скрипт идёт по шагам 1/9 … 9/9 и печатает каждый. Код выхода: 0 — версия установлена (или уже стояла);
1 — отказ или возврат на прежнюю версию; 2 — ошибка в команде или в `update.conf`.

**Шаги 1–4 — портал работает.** Скрипт получает версии с GitHub и печатает коммит тега, проверяет, что в
установке ничего не правили руками, что версия новее текущей, ставит зависимости новой версии, проверяет,
что для копии базы хватит места, и ждёт конца фоновых задач (сбор hh) до `JOB_WAIT_MIN` минут. Любой отказ здесь
начинается словами «Обновление не начато, портал работает» и называет причину:

| Сообщение | Что делать |
|---|---|
| ручные правки, список файлов (` M …`, `?? …`) | правки на сервере не допускаются: пришлите список разработчику; ваше решение — в новой версии |
| версия … не найдена в репозитории | проверьте номер: `git tag --list 'v*'` |
| … старше установленной … | назад — только `rollback.sh` (раздел 4) |
| мало места … нужно N МБ | освободите место в `BACKUP_DIR` или смените каталог в `update.conf` |
| под копию базы нет места … или её размер не узнать | причина — строкой выше: «мало места» или «не удалось узнать размер базы» (база недоступна) |
| фоновая задача идёт дольше N мин | дождитесь конца сбора и повторите |
| не удалось получить версии из репозитория | сеть или ключ GitHub (раздел 2.1) |
| `server/.venv` — не ссылка | не пройден раздел 2 «Первый раз» |
| (выход 2) `update.conf` могут менять другие пользователи | `chmod 600 server/update.conf` |

После отказа на шагах 2–4 могут остаться `.releases/<тег>` и `server/.venvs/<тег>` — это нормально:
следующий запуск пересоздаст первый и возьмёт готовый второй.

**Шаг 5 — остановка и копия.** Таймеры и портал останавливаются; если в новой версии есть миграции, пишется
копия базы. Копия не записалась — «Обновление не начато … Портал и таймеры запускаются снова», прежняя копия
цела. Скрипт запускает портал, но не ждёт ответа: через несколько секунд проверьте
`curl -s http://127.0.0.1:8000/api/version`.

**Шаги 6–7 — код, миграции, запуск.** Не прошло (миграция упала, портал не ответил новой версией за
`START_WAIT_S`) — скрипт сам возвращает прежнюю версию и пишет «Обновление не прошло, работает vX, база
обновлена и совместима, копия — …». Прежняя версия на обновлённой базе работает штатно. Пришлите разработчику
вывод скрипта; базу из копии **не** восстанавливайте.

**Шаг 9 — итог одним экраном:** было → стало, применённые миграции, заметки о настройках («настройка … оставлена
как есть» — её меняли в портале, новое умолчание не применено), переменные из `.env.example`, которых нет в
`.env` (только имена), «Ручные шаги» всех пропущенных версий, имя копии базы. Ручные шаги выполните сразу.

**Если обновление прервалось** (оборвался SSH без `tmux`, процесс убили). Обрыв SSH на шагах 5–7 скрипт
ловит сам: возвращает прежнюю версию и запускает портал, как при любом провале; вывод после обрыва — в
`BACKUP_DIR/update.log`. Если процесс убили так, что
он не успел ничего вернуть, запустите **ту же команду ещё раз**: код уже на новой версии, скрипт это видит и
доводит шаги 6–7 — ссылку на зависимости, оставшиеся миграции, запуск и проверку — и пишет «Обновление до vX
доведено». С `rollback.sh` так же: повторный запуск доводит откат. Если и повторный запуск пишет «Установка …
не доведена: <причина>» (у отката — «Откат … не доведён»), портал может быть остановлен: пришлите вывод разработчику, а пока верните прежнюю
версию вручную — `git checkout -q --detach <прежняя>`, `ln -sfn .venvs/<прежняя> server/.venv`, запуск служб
(база после миграций с прежней версией совместима).

Можно перескочить через версии (`v1.0.0 → v1.2.0`): миграции применятся по порядку, ручные шаги покажутся
для всех.

## 4. Откат на прошлую версию

```bash
cd ~/projects/HR-agent
tmux new -A -s update
bash server/scripts/rollback.sh v1.1.0
```

Меняется только код, база не трогается: миграции новой версии остаются в базе («миграции новее кода
остаются в базе: …»), прошлая версия с ними работает. Интернет не нужен, если каталог зависимостей прошлой
версии на месте (он хранится); нет — ставится до остановки портала.

Откат откажет, если:
- версия ниже v1.1.0 (у v1.0.0 нет журнала версий; если не удалось обновление с v1.0.0, его вернул
  `update.sh`);
- версия старше той, с которой обновлялись последний раз — откат только на одну ступень;
- у пропускаемой версии в `CHANGELOG.md` написано «Откат: нет» — вернуться можно только восстановлением базы
  (раздел 6), решение — с разработчиком;
- идёт фоновая задача, есть ручные правки — как в разделе 3.

Не прошёл откат (прошлая версия не ответила) — скрипт возвращает текущую и пишет «Откат не прошёл, работает
vX, база не менялась». Вернуться после отката вперёд — `update.sh <прежняя версия>`.

## 5. Копия базы

- Одна: `BACKUP_DIR/ruware.dump` и `ruware.dump.info` (версия кода, время, размер). Каталог 700, файл 600.
- Пишется по таймеру (раздел 2.8) и `update.sh` перед миграциями; вручную — `bash server/scripts/db_copy.sh`.
- Новая пишется в `ruware.dump.new`, проверяется (`pg_restore --list`, размер) и только потом заменяет
  прежнюю. Мало места, ошибка pg_dump, идёт обновление — выход 1, прежняя копия цела.
- Результат каждой копии — в истории задач портала («Схема», задача `db_copy`) и `systemctl --user status
  ruware-db-copy`.
- Нужно место ≥ размер базы × `SPACE_FACTOR`. История копий и вынос на другой сервер — забота резервного
  копирования ИТ.

## 6. Восстановление базы из копии вручную

Только на крайний случай — база испорчена или потеряна. Всё, что сделали после времени в `ruware.dump.info`
(решения рекрутеров, новые резюме), пропадёт. Обычная неудача обновления базу не портит — см. раздел 3.

```bash
cd ~/projects/HR-agent
. server/update.conf                         # STOP_CMD, START_CMD, BACKUP_DIR
cat "$BACKUP_DIR/ruware.dump.info"           # от какой версии и какого времени копия
eval "$STOP_CMD"
psql -d postgres -c 'ALTER DATABASE ruware_hr RENAME TO ruware_hr_broken'    # испорченную — в сторону
createdb ruware_hr
pg_restore --no-owner -d ruware_hr "$BACKUP_DIR/ruware.dump"
set -a; . server/.env; set +a
server/.venv/bin/python -m hr.cli migrate    # доводит базу до версии кода, если код новее копии
eval "$START_CMD"
curl -s http://127.0.0.1:8000/api/version
```

Для базы в Docker — те же команды через `docker exec -i ruware-db …`, копия подаётся на вход:
`docker exec -i ruware-db pg_restore -U postgres --no-owner -d ruware_hr < "$BACKUP_DIR/ruware.dump"`.
`psql`, `createdb`, `pg_restore` подключаются так же, как `PG_DUMP` в `update.conf` (`-h … -p … -U …`).
Восстанавливает пользователь, которому можно создавать базы и расширения `vector` и `pg_trgm`. Проверили
работу — удалите `ruware_hr_broken` (`dropdb ruware_hr_broken`); места на две базы нет — удалите её до
`createdb`.

## 7. Переход на v1.2.0: поиск по смыслу

Что меняется для админа: на сервере портала появляется вторая служба — **bge-m3**, она превращает тексты
резюме и профилей в векторы (так портал находит похожих по смыслу). Тексты резюме — персональные данные,
поэтому служба работает на том же сервере и слушает только `127.0.0.1`: наружу и в интернет резюме не уходят.
Языковая модель `t-lite:2.1` остаётся на 10.20.10.6, ей уходят только названия должностей и ключевые слова.

Порядок: 7.1 → 7.2 → 7.3 — до `update.sh`, потом 7.4 — обновление, 7.5 — проверка.

### 7.1. Служба bge-m3: text-embeddings-inference на процессоре

Берём готовый образ Hugging Face `text-embeddings-inference` (TEI) для процессора. Видеокарта не нужна,
памяти — около 3–4 ГБ.

**Выбрать и закрепить образ.** Номер версии CPU-образа смотрите на странице выпусков
https://github.com/huggingface/text-embeddings-inference/releases — тег вида `cpu-1.N` (последний выпуск,
вышедший не меньше двух недель назад). Образ закрепляется по **digest** — отпечатку, который не меняется,
даже если тег перезапишут:

```bash
docker pull ghcr.io/huggingface/text-embeddings-inference:cpu-1.N      # 1.N — с той страницы
docker inspect --format '{{index .RepoDigests 0}}' ghcr.io/huggingface/text-embeddings-inference:cpu-1.N
# ghcr.io/huggingface/text-embeddings-inference@sha256:<64 знака>  — это и есть закреплённый образ
```

Строку `…@sha256:…` запишите в журнал сервера (где ведёте учёт установленного) вместе с датой и тегом. Дальше
везде используйте её, а не тег.

**Закрепить веса модели.** На https://huggingface.co/BAAI/bge-m3/tree/main → «History» скопируйте полный
номер последнего коммита (40 знаков) — это ревизия весов. Тоже в журнал.

**Запуск.** Порт — любой свободный, ниже — 8081; веса при первом старте скачиваются с huggingface.co в каталог
`/srv/bge-m3` (около 2,3 ГБ, несколько минут), дальше берутся оттуда.

```bash
sudo mkdir -p /srv/bge-m3 && sudo chown "$USER" /srv/bge-m3
docker run -d --name ruware-bge-m3 --restart unless-stopped \
  -p 127.0.0.1:8081:80 -v /srv/bge-m3:/data \
  ghcr.io/huggingface/text-embeddings-inference@sha256:<digest> \
  --model-id BAAI/bge-m3 --revision <ревизия весов>
docker logs -f ruware-bge-m3     # ждите строки о готовности (Ready), Ctrl+C — выйти из просмотра
```

Обязательно `127.0.0.1:` перед портом: без него Docker откроет службу всей сети. Проверка:

```bash
curl -s http://127.0.0.1:8081/v1/embeddings -H 'Content-Type: application/json' \
  -d '{"model": "BAAI/bge-m3", "input": ["инженер-электроник"]}' | head -c 200
# в ответе есть "embedding":[0.0…, — служба работает; ошибка соединения — служба ещё не готова
ss -ltn | grep 8081   # адрес только 127.0.0.1:8081, не 0.0.0.0
```

Ночной пересчёт занимает процессор с 02:30 до 06:30. Если днём портал медленнее обычного, ограничьте службу
ядрами: при запуске добавьте `--cpus 6` (из восьми).

### 7.2. Проверка образа как новой зависимости

Образ TEI — новая сторонняя программа на сервере с персональными данными, поэтому до запуска в работу его
проверяют сканером уязвимостей, как зависимости портала. Подойдёт бесплатный Trivy (без регистрации):

```bash
trivy image --severity CRITICAL,HIGH ghcr.io/huggingface/text-embeddings-inference@sha256:<digest>
```

Находок CRITICAL и HIGH нет — запишите в журнал «проверено, дата, digest». Есть — пришлите список
разработчику до обновления: решаем вместе (другой выпуск образа или принятый риск с записью). Повторять при
каждой смене digest.

### 7.3. Строки `server/.env`

Добавьте или поправьте (значения ключей никуда не пересылайте):

```bash
EMBED_BASE_URL=http://127.0.0.1:8081/v1
EMBED_MODEL=BAAI/bge-m3
EMBED_TIMEOUT_S=60
LLM_BASE_URL=http://10.20.10.6:11434/v1

LLM_API_KEY=
```

`LLM_API_KEY` для Ollama можно оставить пустым или написать `ollama`. Порт в `EMBED_BASE_URL` — тот, что
в 7.1. Без `EMBED_BASE_URL` портал работает как раньше, но без близости по смыслу.

### 7.4. Обновление и ночной таймер

```bash
cd ~/projects/HR-agent
tmux new -A -s update
bash server/scripts/update.sh v1.2.0
```

Миграция `010_semantic_search.sql` только добавляет таблицы, копия базы пишется перед ней, как обычно.

В v1.2.0 новая ночная задача — пересчёт векторов (`ruware-reembed-night.timer`, каждый день в 02:30 по
Москве, до 06:30). Таймер ставит `install_autostart.sh`:

```bash
cd ~/projects/HR-agent
cp server/scripts/install_autostart.sh ~/install_autostart.sh
nano ~/install_autostart.sh       # пути APP, PG, DATA и DATABASE_URL в начале — как у вас
bash ~/install_autostart.sh       # портал перезапустится на несколько секунд
systemctl --user list-timers | grep reembed   # следующий запуск — ближайшие 02:30
```

Копия скрипта — вне репозитория: правка самого `server/scripts/install_autostart.sh` — ручная правка
установки, и следующее обновление откажет. Если службы у вас поставлены иначе (системные службы, cron) —
заведите задачу `python -m hr.cli run reembed_night` на 02:30 своим способом, без догона пропущенного запуска.

После этого допишите `ruware-reembed-night.timer` в строку `TIMERS` в `server/update.conf` (как в
`server/update.conf.example`), чтобы обновления останавливали и его. Раньше установки таймера не дописывайте:
остановка несуществующего таймера даёт ошибку.

### 7.5. Проверка после обновления

```bash

.venv/bin/python -m hr.cli hh-selftest   # «hh отвечает, токен действует.»
```

В портале под руководителем отдела персонала откройте «Схему»:

- плитки «Полных резюме hh сегодня … / 300» и «Запросов к модели сегодня … / 500»;
- строка «Пересчёт векторов базы: осталось N из M резюме» — это нормально до конца первых ночей;
- строки «Модель векторов недоступна с …» быть не должно. Есть — служба bge-m3 не отвечает: `docker ps`,

«База должностей» → любой профиль → «Синонимы ключей» → «Предложить синонимы»: через минуту появятся
предложения. «Модель сейчас недоступна» — не отвечает `t-lite:2.1` на 10.20.10.6 (`LLM_BASE_URL`,
`LLM_MODEL`); вписывать синонимы руками можно и без неё.

**Утром после первой ночи** — в «Схеме» у задачи «Пересчёт векторов» прогон в 02:30 и итог; число «осталось»
уменьшилось. Вся база (около 15 тыс. резюме) пересчитывается за одну-несколько ночей. Итог «служба векторов не отвечает: 3 отказа
подряд» — служба bge-m3 падала ночью: `docker logs ruware-bge-m3`, хватает ли памяти.

### 7.6. Если модель мешает: выключить объяснения моделью

Объяснения балла, черновики писем и разбор замечаний можно перевести на шаблон, не трогая синонимы:

```bash

.venv/bin/python -m hr.cli setting set llm_assist_enabled false --by <ваш логин в портале>
# включить обратно — то же с true
```

Правка пишется в журнал изменений (кто и когда) и обновлением не перетирается. Пределы на сутки — тоже
настройки той же командой: `llm_calls_per_day` (500), `llm_explain_per_day` (300 фоновых объяснений
внутри общих 500), `llm_synonyms_per_day` (100),
`hh_full_resume_per_day` (300 из 500 просмотров компании: остаток — рекрутерам на сайте hh).

## 8. Переход на v1.3.0: воронка по этапам

Что меняется для админа: на сервере — ничего нового. Новых служб, таймеров и строк `.env` нет, обновление —
обычное (раздел 3). Меняется работа отдела персонала: воронка вакансии теперь идёт по этапам, рекрутер отмечает
у каждого этапа «прошёл», «не прошёл» или «отказался» с причиной, а портал считает по этим отметкам отчёт в
форме их Excel. Языковая модель в воронке не участвует.

### 8.1. Обновление

```bash
cd ~/projects/HR-agent
tmux new -A -s update
bash server/scripts/update.sh v1.3.0
```

Копия базы пишется перед миграцией, как обычно. Миграция `012_funnel_stages.sql` идёт несколько секунд и
делает три вещи:

1. Заводит новые таблицы в схеме `ops`: справочник этапов, наборы этапов вакансий, отметки кандидатов, паузы
   вакансий. Старые таблицы не меняются.
2. Даёт руководителю отдела персонала новое право `stage.approve` — утверждать наборы этапов и отменять любую
   отметку. Запись об этом появится в «Журнале изменений».
3. Переносит текущую работу. Каждой открытой вакансии и вакансии на паузе — стандартный набор из 8 этапов
   (версия 1, уже утверждён). Каждому кандидату в работе — этап по его нынешнему статусу, без истории:

| Статус до обновления | Этап после |
|---|---|
| Отобран агентом | Отобранные резюме |
| Написали, Ответил | Первичный контакт |
| Телефонное интервью | Пройденное первичное интервью |
| Встреча с руководителем, Тестовое задание | Собеседование |
| Проверка СБ | Проверка СБ |
| Оффер | Оффер |

Кандидаты «Новый», «Резерв» и закрытые (вышел на работу, отказ) этапа не получают. Кандидат сразу в нескольких
вакансиях встаёт на свой этап в той вакансии, куда его добавили последней, в остальных — на «Отобранные
резюме». Отчёт воронки считается с даты обновления — под отчётом рекрутеры увидят «Учёт с <дата>».

### 8.2. Проверка после обновления

```bash
cd ~/projects/HR-agent/server
set -a; . ./.env; set +a
.venv/bin/python -m hr.cli version        # «версия кода: v1.3.0 …», «неприменённых нет»
.venv/bin/python -m hr.cli funnel-carry   # «перенесено: наборов этапов: 0, отметок: 0» — перенос уже сделан
```

Повторный перенос ничего не меняет, поэтому вторая команда безопасна: нули значат, что миграция всё перенесла.

В портале под руководителем отдела персонала:

- вкладка **«Воронка»** открывается отчётом **«Весь отдел»** за текущий год: 8 строк «Вошли · Прошли · %»,
  внизу «Конверсия воронки» и «Учёт с <дата обновления>». Цифры в первые дни маленькие — это нормально,
  прошлое не переносилось;
- **«Вакансии»** → любая открытая → «Воронка»: сверху переключатель **«Кандидаты / Отчёт / Этапы»**. На
  «Кандидатах» люди стоят по этапам, как в таблице выше; на «Отчёте» — та же таблица из 8 строк по этой
  вакансии; на «Этапах» — «Действует» с пометкой «стандартный»;
- «Схема» → «Как работает портал» — внизу «Версия v1.3.0 · …».

Ошибка или пустая страница вместо «Воронки» — пришлите разработчику вывод `update.sh` и снимок экрана.

### 8.3. Что увидят рекрутеры

- Доска вакансии — по этапам её набора; вместо «Перевести» — окно **«Итог этапа»**: прошёл, не прошёл,
  отказался, причина из списка. Назад и через этап перевести нельзя.
- Ошибочную отметку можно отменить: свою — в тот же день, позже и чужую — руководитель отдела персонала.
- Свой набор этапов (например, 4 собеседования без проверки СБ) рекрутер предлагает на вкладке «Этапы»,
  руководитель отдела персонала утверждает на «Воронке» в блоке «Ждут утверждения».
- Вакансию можно поставить на паузу: дни паузы не входят в срок ведения.
- Рекрутер видит только свой отчёт; весь отдел и сравнение рекрутеров — руководитель отдела персонала.

Перед обновлением раздайте отделу персонала мануал рекрутера v2.3: в разделе 7 — памятка «Что изменилось в
воронке с v1.3.0». Руководителям подразделений — мануал руководителя v1.2: их доска вакансии только для чтения,
как и раньше.

### 8.4. Откат на v1.2.0 и возврат

`bash server/scripts/rollback.sh v1.2.0`, как в разделе 4: база не трогается. Статус кандидата v1.3.0 пишет
вместе с каждой отметкой, поэтому старая доска v1.2.0 показывает людей на верных этапах. После отката нет
этапов и наборов, итогов с причинами, отмены отметки, паузы и отчётов. Вакансия на паузе в v1.2.0 видна с
плашкой «на паузе», снять паузу можно только в v1.3.0.

Возврат — `update.sh v1.3.0`, миграция уже применена, поэтому перенос нужно запустить руками:

```bash
cd ~/projects/HR-agent/server
set -a; . ./.env; set +a
.venv/bin/python -m hr.cli funnel-carry   # «перенесено: наборов этапов: N, отметок: M»
```

Команда ставит на этапы кандидатов и вакансии, которые завели в v1.2.0 после отката, так же, как миграция при
первом обновлении. **Ограничение:** кандидата, у которого в этой вакансии уже есть отметки v1.3.0, команда не
трогает. Если в v1.2.0 его перевели дальше или закрыли, после возврата он стоит на этапе, где был до отката, —
предупредите рекрутеров: такие карточки они доводят сами окном «Итог этапа». Вакансия, которую в v1.2.0 открыли
заново, считает срок ведения вместе с днями, пока была закрыта.
