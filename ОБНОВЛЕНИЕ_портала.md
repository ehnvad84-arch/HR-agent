# Обновление портала подбора «Рувер»

Для инженера, который обслуживает портал на сервере компании. Версия от 10.11.2026, для v1.1.0 и новее.
Шаги проверены репетицией на пробном сервере: установка v1.0.0 из архива → переход → обновления → отказы →
откат. Установка с нуля — `УСТАНОВКА_на_сервер.md`, что нового в каждой версии — `CHANGELOG.md`.

Ниже каталог установки — `~/projects/HR-agent` (как в инструкции по установке), команды — от пользователя,
под которым работают службы портала. Ключи и пароли из `.env` никуда не пересылаются и в чаты не вставляются.

## 1. Как устроено

- Каждая версия — тег `vX.Y.Z` в репозитории GitHub: Z — исправления, Y — новые возможности, X — несовместимые
  изменения. Номер работающей версии — внизу «Схемы» → «Как работает портал» и по адресу `/api/version`.
- Установка — копия репозитория на теге. Сервер берёт версии ключом GitHub **только на чтение**; агент
  разработки доступа к серверу не имеет.
- Обновление — одна команда `update.sh`: проверки, пока портал работает → остановка → копия базы → код,
  зависимости, миграции → запуск и проверка. Не прошло — портал сам возвращается на прежнюю версию.
- Миграции только добавляют: прошлая версия работает на базе новой. Поэтому откат (`rollback.sh`) меняет
  только код, базу не трогает, и всё, что рекрутеры сделали после обновления, остаётся.
- На каждую версию — свой каталог зависимостей `server/.venvs/<тег>`, `server/.venv` — ссылка на текущий.
  Хранятся текущий и прошлый: откат идёт за секунды и без интернета.
- Копия базы на сервере одна и свежая: пишется раз в неделю таймером и перед каждым обновлением с
  миграциями. Новая заменяет прежнюю только после проверки.

Портал на время обновления недоступен несколько минут: обновляйте вечером или до 8:00, не в 18:00 (сбор hh).

## 2. Первый раз: установка из архива становится копией репозитория

Нужен один раз на сервере, где v1.0.0 стоит из ZIP-архива (без каталога `.git`). Службы, база, `.env` и
файлы в `server/data` не меняются; пути служб и программ тоже.

### 2.1. Ключ GitHub только на чтение

```bash
ssh-keygen -t ed25519 -N "" -C "ruware-<имя сервера>" -f ~/.ssh/ruware_github
chmod 600 ~/.ssh/ruware_github
cat ~/.ssh/ruware_github.pub
```

Строку `ssh-ed25519 AAAA…` отправьте владельцу репозитория: он добавит её в Settings → Deploy keys **без**
«Allow write access». Закрытый ключ (`ruware_github` без `.pub`) с сервера не уходит.

В `~/.ssh/config` (права 600):

```
Host github.com
  HostName github.com
  User git
  IdentityFile ~/.ssh/ruware_github
  IdentitiesOnly yes
  StrictHostKeyChecking yes
```

Ключ сервера GitHub — в `~/.ssh/known_hosts`, сверенный с опубликованным отпечатком:

```bash
ssh-keyscan -t ed25519 github.com > /tmp/gh.key && ssh-keygen -lf /tmp/gh.key
# отпечаток обязан совпасть с SHA256 для ED25519 на странице
# https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/githubs-ssh-key-fingerprints
cat /tmp/gh.key >> ~/.ssh/known_hosts && rm /tmp/gh.key
ssh -T git@github.com    # «Hi ehnvad84-arch/HR-agent! You've successfully authenticated…» — ключ работает
```

Не совпал отпечаток — дальше не идите, сообщите владельцу репозитория.

### 2.2. Клон рядом с установкой на v1.0.0

```bash
cd ~/projects
git clone git@github.com:ehnvad84-arch/HR-agent.git HR-agent-git
git -C HR-agent-git checkout v1.0.0
git -C HR-agent-git describe --tags          # v1.0.0
```

### 2.3. Сверка: в архиве то же, что в теге v1.0.0

```bash
diff -r -q -x .git -x .env -x data -x .venv -x __pycache__ -x .pytest_cache -x .ruff_cache \
  ~/projects/HR-agent ~/projects/HR-agent-git && echo "расхождений нет"
```

Ожидается «расхождений нет». Любая строка `Files … differ` или `Only in …` — **стоп**: на сервере что-то
правили руками. Пришлите список разработчику и ждите решения; клон можно просто удалить.

### 2.4. Перенос и переименование (портал остановлен)

```bash
cd ~/projects
TIMERS="ruware-hh-daily.timer ruware-trudvsem.timer ruware-load-watchdog.timer ruware-feedback-week.timer ruware-staff-sync.timer"
systemctl --user stop $TIMERS && systemctl --user stop ruware-portal.service

mv HR-agent/server/.env  HR-agent-git/server/.env
mv HR-agent/server/data  HR-agent-git/server/data
mkdir -p HR-agent-git/server/.venvs
mv HR-agent/server/.venv HR-agent-git/server/.venvs/v1.0.0
ln -s .venvs/v1.0.0 HR-agent-git/server/.venv
printf '%s\n' .venv .venvs/ .releases/ update.conf >> HR-agent-git/.git/info/exclude

mv HR-agent HR-agent-zip
mv HR-agent-git HR-agent
```

Если службы у вас называются иначе или портал — системная служба, остановите их своими командами.
Последняя строка `printf` нужна: у v1.0.0 в `.gitignore` нет ссылки `.venv` и каталогов обновления, без неё
`git status` не будет чистым и `update.sh` откажет.

### 2.5. Запуск и проверка

```bash
systemctl --user start ruware-portal.service && systemctl --user start $TIMERS
cd ~/projects/HR-agent
git describe --tags                     # v1.0.0
git status --porcelain                  # пусто
curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8000/   # 200 (через несколько секунд после запуска)
```

У v1.0.0 нет команды `hr.cli version` и адреса `/api/version` — это нормально. Запись о версии в журнал
версий сделает первое обновление. `HR-agent-zip` удалите после первого удачного обновления.

### 2.6. Настройки обновления `server/update.conf`

Образца у v1.0.0 нет — берётся из тега v1.1.0:

```bash
cd ~/projects/HR-agent
git fetch --tags origin
(umask 077; git show v1.1.0:server/update.conf.example > server/update.conf)
nano server/update.conf
```

Заполните: `STOP_CMD` и `START_CMD` (таймеры и портал, как у вас устроено: образец — systemd пользователя,
второй вариант — системная служба и cron), `BACKUP_DIR` — каталог копии базы **вне** репозитория и не в общих
папках (в копии все персональные данные), `PG_DUMP` — pg_dump 16 с вашей базой (на сервере или
`docker exec …`), пароль базы — в `~/.pgpass` (600), не в этом файле. Файл — 600: в нём исполняемые команды.

### 2.7. Первое обновление — на v1.1.0

В v1.0.0 скрипта обновления нет, поэтому первый раз он берётся из тега:

```bash
cd ~/projects/HR-agent
tmux new -A -s update     # обрыв SSH не прервёт обновление; tmux нет — sudo apt install tmux
git fetch --tags origin && git show v1.1.0:server/scripts/update.sh > /tmp/ruware-update.sh \
  && bash /tmp/ruware-update.sh v1.1.0
```

Дальше — как в разделе 3. После него: `server/.venv/bin/python -m hr.cli version` показывает v1.1.0,
`curl -s http://127.0.0.1:8000/api/version` — `{"version":"v1.1.0","date":"2026-11-10"}`.

### 2.8. Недельный таймер копии базы

Образец юнитов — в конце `server/update.conf.example` (`ruware-db-copy.service` и `.timer`, воскресенье 03:00).
Поправьте в нём `WorkingDirectory` на каталог установки, положите файлы в `~/.config/systemd/user/` и
включите:

```bash
systemctl --user daemon-reload && systemctl --user enable --now ruware-db-copy.timer
systemctl --user start ruware-db-copy.service && ls -l "$BACKUP_DIR"   # проверка: ruware.dump и ruware.dump.info
```

## 3. Обычное обновление

Номер новой версии и её «Ручные шаги» — в `CHANGELOG.md` (`git fetch --tags origin && git show
vX.Y.Z:CHANGELOG.md | head -40`).

```bash
cd ~/projects/HR-agent
tmux new -A -s update     # обрыв SSH не прервёт обновление; вернуться — та же команда
bash server/scripts/update.sh v1.2.0
```

Скрипт идёт по шагам 1/9 … 9/9 и печатает каждый. Код выхода: 0 — версия установлена (или уже стояла);
1 — отказ или возврат на прежнюю версию; 2 — ошибка в команде или в `update.conf`.

**Шаги 1–4 — портал работает.** Скрипт получает версии с GitHub и печатает коммит тега, проверяет, что в
установке ничего не правили руками, что версия новее текущей, ставит зависимости новой версии, проверяет,
что для копии базы хватит места, и ждёт конца фоновых задач (сбор hh) до `JOB_WAIT_MIN` минут. Любой отказ здесь
начинается словами «Обновление не начато, портал работает» и называет причину:

| Сообщение | Что делать |
|---|---|
| ручные правки, список файлов (` M …`, `?? …`) | правки на сервере не допускаются: пришлите список разработчику; ваше решение — в новой версии |
| версия … не найдена в репозитории | проверьте номер: `git tag --list 'v*'` |
| … старше установленной … | назад — только `rollback.sh` (раздел 4) |
| мало места … нужно N МБ | освободите место в `BACKUP_DIR` или смените каталог в `update.conf` |
| под копию базы нет места … или её размер не узнать | причина — строкой выше: «мало места» или «не удалось узнать размер базы» (база недоступна) |
| фоновая задача идёт дольше N мин | дождитесь конца сбора и повторите |
| не удалось получить версии из репозитория | сеть или ключ GitHub (раздел 2.1) |
| `server/.venv` — не ссылка | не пройден раздел 2 «Первый раз» |
| (выход 2) `update.conf` могут менять другие пользователи | `chmod 600 server/update.conf` |

После отказа на шагах 2–4 могут остаться `.releases/<тег>` и `server/.venvs/<тег>` — это нормально:
следующий запуск пересоздаст первый и возьмёт готовый второй.

**Шаг 5 — остановка и копия.** Таймеры и портал останавливаются; если в новой версии есть миграции, пишется
копия базы. Копия не записалась — «Обновление не начато … Портал и таймеры запускаются снова», прежняя копия
цела. Скрипт запускает портал, но не ждёт ответа: через несколько секунд проверьте
`curl -s http://127.0.0.1:8000/api/version`.

**Шаги 6–7 — код, миграции, запуск.** Не прошло (миграция упала, портал не ответил новой версией за
`START_WAIT_S`) — скрипт сам возвращает прежнюю версию и пишет «Обновление не прошло, работает vX, база
обновлена и совместима, копия — …». Прежняя версия на обновлённой базе работает штатно. Пришлите разработчику
вывод скрипта; базу из копии **не** восстанавливайте.

**Шаг 9 — итог одним экраном:** было → стало, применённые миграции, заметки о настройках («настройка … оставлена
как есть» — её меняли в портале, новое умолчание не применено), переменные из `.env.example`, которых нет в
`.env` (только имена), «Ручные шаги» всех пропущенных версий, имя копии базы. Ручные шаги выполните сразу.

**Если обновление прервалось** (оборвался SSH без `tmux`, процесс убили). Обрыв SSH на шагах 5–7 скрипт
ловит сам: возвращает прежнюю версию и запускает портал, как при любом провале; вывод после обрыва — в
`BACKUP_DIR/update.log`. Если процесс убили так, что
он не успел ничего вернуть, запустите **ту же команду ещё раз**: код уже на новой версии, скрипт это видит и
доводит шаги 6–7 — ссылку на зависимости, оставшиеся миграции, запуск и проверку — и пишет «Обновление до vX
доведено». С `rollback.sh` так же: повторный запуск доводит откат. Если и повторный запуск пишет «Установка …
не доведена: <причина>» (у отката — «Откат … не доведён»), портал может быть остановлен: пришлите вывод разработчику, а пока верните прежнюю
версию вручную — `git checkout -q --detach <прежняя>`, `ln -sfn .venvs/<прежняя> server/.venv`, запуск служб
(база после миграций с прежней версией совместима).

Можно перескочить через версии (`v1.0.0 → v1.2.0`): миграции применятся по порядку, ручные шаги покажутся
для всех.

## 4. Откат на прошлую версию

```bash
cd ~/projects/HR-agent
tmux new -A -s update
bash server/scripts/rollback.sh v1.1.0
```

Меняется только код, база не трогается: миграции новой версии остаются в базе («миграции новее кода
остаются в базе: …»), прошлая версия с ними работает. Интернет не нужен, если каталог зависимостей прошлой
версии на месте (он хранится); нет — ставится до остановки портала.

Откат откажет, если:
- версия ниже v1.1.0 (у v1.0.0 нет журнала версий; если не удалось обновление с v1.0.0, его вернул
  `update.sh`);
- версия старше той, с которой обновлялись последний раз — откат только на одну ступень;
- у пропускаемой версии в `CHANGELOG.md` написано «Откат: нет» — вернуться можно только восстановлением базы
  (раздел 6), решение — с разработчиком;
- идёт фоновая задача, есть ручные правки — как в разделе 3.

Не прошёл откат (прошлая версия не ответила) — скрипт возвращает текущую и пишет «Откат не прошёл, работает
vX, база не менялась». Вернуться после отката вперёд — `update.sh <прежняя версия>`.

## 5. Копия базы

- Одна: `BACKUP_DIR/ruware.dump` и `ruware.dump.info` (версия кода, время, размер). Каталог 700, файл 600.
- Пишется по таймеру (раздел 2.8) и `update.sh` перед миграциями; вручную — `bash server/scripts/db_copy.sh`.
- Новая пишется в `ruware.dump.new`, проверяется (`pg_restore --list`, размер) и только потом заменяет
  прежнюю. Мало места, ошибка pg_dump, идёт обновление — выход 1, прежняя копия цела.
- Результат каждой копии — в истории задач портала («Схема», задача `db_copy`) и `systemctl --user status
  ruware-db-copy`.
- Нужно место ≥ размер базы × `SPACE_FACTOR`. История копий и вынос на другой сервер — забота резервного
  копирования ИТ.

## 6. Восстановление базы из копии вручную

Только на крайний случай — база испорчена или потеряна. Всё, что сделали после времени в `ruware.dump.info`
(решения рекрутеров, новые резюме), пропадёт. Обычная неудача обновления базу не портит — см. раздел 3.

```bash
cd ~/projects/HR-agent
. server/update.conf                         # STOP_CMD, START_CMD, BACKUP_DIR
cat "$BACKUP_DIR/ruware.dump.info"           # от какой версии и какого времени копия
eval "$STOP_CMD"
psql -d postgres -c 'ALTER DATABASE ruware_hr RENAME TO ruware_hr_broken'    # испорченную — в сторону
createdb ruware_hr
pg_restore --no-owner -d ruware_hr "$BACKUP_DIR/ruware.dump"
set -a; . server/.env; set +a
server/.venv/bin/python -m hr.cli migrate    # доводит базу до версии кода, если код новее копии
eval "$START_CMD"
curl -s http://127.0.0.1:8000/api/version
```

Для базы в Docker — те же команды через `docker exec -i ruware-db …`, копия подаётся на вход:
`docker exec -i ruware-db pg_restore -U postgres --no-owner -d ruware_hr < "$BACKUP_DIR/ruware.dump"`.
`psql`, `createdb`, `pg_restore` подключаются так же, как `PG_DUMP` в `update.conf` (`-h … -p … -U …`).
Восстанавливает пользователь, которому можно создавать базы и расширения `vector` и `pg_trgm`. Проверили
работу — удалите `ruware_hr_broken` (`dropdb ruware_hr_broken`); места на две базы нет — удалите её до
`createdb`.
